# Ozmishow container definitions

These three JSON files are CreateContainer request bodies for the current AutoTable Go implementation. They preserve Ozmishow's current content structure. They do not install the legacy API routes.

## Import

With an authenticated tenant/project management session, submit each file separately to:

`POST /api/v1/{tenantSlug}/{projectSlug}/container/`

Create `pageOptions`, `twoPicture`, and `navbar`. Do not send sample-records.json to this endpoint: it contains optional dynamic data, grouped by schema, not container definitions. No IDs or tenant/project IDs belong in these creation payloads; AutoTable resolves project scope.

Existing projects already have `auth` and `role`; do not create duplicate auth containers. These content routes authorize role names `admin` and `superAdmin`. AutoTable seeds `admin`; create a `superAdmin` role record only if needed. Authentication/login adaptation is separate: AutoTable's default auth uses email, while Ozmishow sends userName.

## Field choices

- `page` remains the English page-name string, not an ObjectId. Renaming a page requires updating its components and parent-name references.
- `language` accepts EN/TR, matching current admin writes.
- `position` uses AutoTable's `int` type, including zero. Ordering indexes are not unique because current reorder operations update records separately.
- `sections` uses `stringArray`; `twoPictureArray` uses `array` (objects).
- Objects and twoPictureArray intentionally have no children definitions. Both legacy styled picture objects and professional section documents must retain arbitrary nested properties. Professional content is stored in twoPictureArray[0]. This supports Ozmishow's custom editor; it does not generate detailed AutoTable forms for each nested component. AutoTable's dedicated child-array editing operations require children metadata; use whole-record PATCH for these payloads, as Ozmishow does.
- Optional aliases mainMainHeader/componentStyle and renderer props/data are included.
- `_id` is generated by MongoDB; do not declare it as an editable field.
- pageNameEN is unique. Navbar singleton behavior must be enforced by the save handler; this schema alone permits multiple records.
- Reads are public; enabled writes require authentication and admin/superAdmin. Omitted operations default to inactive.
- Use `isActive` in these HTTP JSON bodies: RouteSpec has a Go field IsActive with no json tag, although its BSON storage key is isActivated. Do not substitute the BSON key in an HTTP creation request.
- Redis configuration is omitted because CreateContainer replaces it with server defaults (currently caching enabled and self-invalidation). Cross-schema caches and Next.js revalidation still need integration.

## Remaining API integration

AutoTable's generic dynamic endpoints are under `/api/v1/{tenantSlug}/{projectSlug}/dynamic`. They do not automatically expose `/pageOptions/navbar` or `/twoPicture/:page`, or return the legacy `{pageOptions: [...]}` / `{navbar: [...]}` wrappers. A compatibility handler or changes to Ozmishow's API-access layer are still required. Public component reads must resolve a page-name filter and return components in position order. Keep the existing language behavior: Ozmishow currently requests a page without a language query parameter.

Authenticated writes also need actual AutoTable credentials forwarded by the Next.js backend. The current Ozmishow backend helper does not do that. These JSONs configure data and permissions, not that connection.

## Template seed

Optionally insert the records in sample-records.json, one schema at a time, using AutoTable's normal item creation UI/API. The example navbar uses the supported classic variant. Replace the sample content with actual site data before marking the project as a reusable template. Include template items if the cloned project should start with pages/components/navbar; do not copy administrator accounts.
