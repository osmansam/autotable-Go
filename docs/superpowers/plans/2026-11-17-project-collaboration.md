# Tenant Panel Project Collaboration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Native execution is recommended for this plan because the tasks share authorization, transaction, and onboarding interfaces.

**Goal:** Let tenant owners/admins and project admins invite and manage project collaborators with the existing fixed roles, without granting access to unrelated projects or published applications.

**Architecture:** Extend the existing live management authorizer and route contracts. Put all membership grants and changes behind guarded MongoDB transactions; persist audit/revocation events and encrypted email-delivery jobs with the mutation. Use separate account authentication and invitation continuation proofs, then establish existing management-cookie sessions only after acceptance commits.

**Tech Stack:** Go 1.24, Fiber v2, existing MongoDB Go driver v1, MongoDB replica-set transactions, Go standard-library cryptography/TLS/SMTP, React/TypeScript, React Query, existing panel UI, Vitest/Testing Library.

**Spec:** `docs/superpowers/specs/2026-11-17-project-collaboration-design.md`, revision 2, approved 2026-11-17.

## Global Constraints

- Scope: **Tenant Panel and visual builders, using the existing fixed project roles**. Published-app identities, runtime OAuth, row/field/workflow rules, and runtime WebSockets remain separate.
- Existing per-project allowlists in `managementPermissionRoles` remain the source of truth. Preserve narrower deletion, credential, integration, and audit restrictions.
- Tenant membership establishes eligibility; evaluate tenant and project role sets separately. Unknown roles grant nothing; legacy role sets are preserved until explicit conversion.
- Invitations cannot reset credentials, change an existing account's email, attach identity providers, or serve as account recovery.
- Invitation entropy: at least 32 cryptographically random bytes. Invitation lifetime: seven days. Account reauthentication freshness: five minutes. Continuation lifetime: the earlier of thirty minutes or invitation expiry.
- Delivery retries: exponential delays capped at one hour, at most ten attempts, never beyond invitation expiry. SMTP acceptance is not confirmed inbox delivery or exactly-once delivery.
- Persist only invitation hashes in invitations; encrypted secrets exist only in outstanding delivery jobs. No raw tokens in browser storage, query strings, OAuth state, query-cache keys, logs, audit, or administration responses.
- Require transaction-capable MongoDB. Real replica-set concurrency tests are a release requirement; no standalone partial-write fallback.
- User, tenant, project, and membership mutations that affect authorization must share the transaction guards, including existing lifecycle writers. Offline direct-database maintenance pauses grants and requires reconciliation.
- No production migrations, deployments, real invitation sends, or secret provisioning are authorized by this local implementation plan.
- Preserve seven-day invitations and existing Editor page/translation behavior; no custom roles, delegated invitation flags, team inheritance, billing seats, or simultaneous editing.

## Review Focus

1. Accounts whose normalized email collides during acceptance: preserve the existing account and require its credentials; never merge, overwrite, or create an extra tenant (Task 7/8 tests).
2. Revoked/rotated invitations while an email job or browser continuation is already active: delivered obsolete links and old continuations must never grant access (Tasks 6/8 tests).
3. Two active admins changing roles/removing each other while a legacy delete/status writer runs: serialize changes and leave a usable admin or an intentionally inactive project (Tasks 3/4 tests).
4. Browser reload, wrong-account login, and project switch with an unsaved builder open: retain only server-side continuation and stop writes from stale scopes/roles (Tasks 8/11 tests).
5. Legacy Support/multiple/unknown role arrays and mixed tenant roles: preserve roles, require explicit conversion, and honor only the correct scope's allowlists (Tasks 1/4/10 tests).

## Shared contracts and implementation choices

These are builder choices implementing the approved design, not new product requirements.

- Keep IDs in service/API inputs as hex strings, validate before repository calls, and use `primitive.ObjectID` for stored models. Reuse `models.ManagementAuthorizationSubject`, `ManagementAuthorizationTarget`, and `ManagementMembershipSnapshot`.
- Add `models.CollaborationAuthority` values `tenant` and `project`. Never infer an OR of both authority modes. A tenant route requires a tenant-scoped management principal; a project route requires the matching project principal.
- Add an explicit permission descriptor for required target/membership scope; preserve `IsProjectPermission` compatibility for existing permissions. New permissions: `tenant.account.read`, `tenant.projects.discover`, `tenant.project.read`, `tenant.project.members.read`, `tenant.project.members.manage`, `project.members.read`, `project.members.manage`. Tenant member-admin permissions require an active target project, but no project membership. Ordinary project detail uses privileged tenant-read roles or the user's explicit active project membership.
- New collections: `management_invitations`, `management_invitation_deliveries`, `management_invitation_continuations`, `management_email_challenges`, `management_collaboration_events`, `management_collaboration_requests`, `management_collaboration_migrations`. Do not reuse runtime dynamic collections or workflow outbox event formats.
- Add `Version int64` to project memberships (legacy absence reads as zero), `AuthorizationVersion int64` to management users/tenants, and `CollaborationVersion int64` to projects. Fields are server-maintained. Missing versions are incrementable without destructive backfill.
- `ProjectCollaborator` is a safe DTO: membership ID, user ID, display name, email, role array, status, version, and created/updated timestamps. No password, token, verification secret, or raw user document.
- Member/invitation directory pagination uses `CollaborationPageRequest{Limit int,AfterID string}` with default limit 20 and maximum 100, validated opaque/ID cursor, and repository-side bounds. `ProjectCollaboratorPage` and `InvitationSummaryPage` contain `Items` of the respective safe DTO type and optional `NextCursor string`, serialized as `items` and `nextCursor`; neither service may fetch an unbounded directory to paginate in memory.
- `RoleChangeInput` contains `Authority models.CollaborationAuthority`, `Actor models.ManagementAuthorizationSubject`, `Target models.ManagementAuthorizationTarget`, `UserID string`, `Role string`, `ExpectedVersion int64`, `ExpectedRoles []string`, `ConvertLegacyRoleSet bool`, `ActivateMembership bool`, and `Reason string`. Activation defaults false and applies only to an existing disabled project membership; it cannot reactivate a disabled user or tenant membership. Legacy role replacement still requires explicit conversion. `RemoveMemberInput` contains the same scope/actor/target/user/version plus reason. `RecoverAdminInput` contains tenant actor/target/user/version and nonempty reason.
- `InvitationSummary` contains ID, tenant/project IDs, invited email, offered single role, lifecycle state, delivery state, version, expiry, and creation/update times. `InvitationPreview` contains only tenant/project display names, offered role, expiry, and generic onboarding state.
- `InvitationIdentityProof` is an internal stored proof with `UserID string`, `NormalizedEmail string`, `AccountVersion int64`, `AuthenticatedAt time.Time`, `ExpiresAt time.Time`, `ContinuationID primitive.ObjectID`, and `EmailVerified bool`. Controllers never deserialize it from request JSON. `AcceptProjectInvitationInput` carries the server-resolved continuation handle/proof plus optional new-account name/password; password is excluded from JSON serialization/logging of internal structs. `AcceptedProjectInvitation` serializes `user`, `tenant`, `allTenants`, `project`, `tenantRoles`, and `roles` (project roles), matching safe existing DTOs. Wrap responses in the existing `status/message/data` envelope.
- `ManagementSessionView` in the panel has `user: User`, `tenant: Tenant`, optional `project: Project`, `roles: string[]`, `roleScope: 'tenant'|'project'`, and `allTenants: Tenant[]`. Task 9 validates these against the selected session endpoint before applying persisted context. Panel `AcceptedProjectInvitation` mirrors the backend Task 8 DTO without any authentication tokens.
- The public invitation flow is local password-based management authentication in this release. Runtime Google OAuth remains unavailable for management proof. No account-recovery implementation is added.
- Collaboration feature flags are server-side: `COLLABORATION_MEMBERS_ENABLED`, `COLLABORATION_INVITATIONS_ENABLED`, `COLLABORATION_RECOVERY_ENABLED`, all false by default. Enabling depends on an applied migration marker and healthy required infrastructure. Frontend reads server feature state rather than enabling capabilities with client flags.
